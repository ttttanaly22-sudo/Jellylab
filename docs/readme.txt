# JellyLab 設計概要

## 目的と構成

JellyLab は Raspberry Pi 上で動かす Flask アプリケーションです。水槽の温度・照度の確認と記録、カメラのライブプレビューと撮影、画像の分類・整理、顕微鏡モードでの写真・動画撮影を提供します。

- `app.py`: Flask アプリ、HTTP ルート、画面と各機能の接続。
- `camera/camera_manager.py`: カメラデバイス、フレーム取得、静止画・動画撮影、カメラ再接続。
- `templates/`: Home、JellyLab、Microscope、タイムラインの画面。
- `sensors/`: DS18B20 温度センサーと BH1750 照度センサーの読み取り。
- `managers/`: センサー統合、定期ログ、画像枚数集計、ストレージ情報。
- `utils/logger.py`: センサー値を日付ごとの CSV に追記。
- `config.py`: カメラ設定、ログ間隔、保存先などの設定。
- `tests/`: Flask ルートの動作確認。
- `docs/`: 運用時の systemd 設定とパッケージ一覧。

## 主な処理

### 起動とカメラ

`app.py` の読み込み時に `CameraManager` を一つ生成します。`CameraManager.__init__()` が設定済みのカメラデバイスを開き、以降 `self.cap` をプレビュー、静止画、動画で共有します。カメラが開けなければ初期化時に例外となり、アプリの起動は失敗します。

### プレビュー

JellyLab と Microscope の画面は `/video` を参照します。Flask の `/video` ルートが MJPEG ストリームを返し、`generate()` が `camera.get_jpeg()` を繰り返し呼び出してフレームを JPEG にして配信します。

### 静止画

- JellyLab の `/capture` は選択されたラベルを付けて `camera.capture()` を呼び、`images/` に保存します。
- Microscope の `/microscope/capture` は `camera.capture()` を呼び、`micro_images/` に保存します。
- `capture()` は共有カメラを一時的に撮影解像度へ切り替えてフレームを取得し、プレビュー解像度に戻してから保存します。

### 動画

Microscope 画面の録画ボタンは `/microscope/video_capture` に開始を依頼し、停止時は `/microscope/video_stop` を呼びます。録画は `CameraManager.start_recording()` が起動するバックグラウンドスレッドで行います。録画スレッドは共有カメラからフレームを読み、いったん mp4v の一時ファイルへ保存します。その後 ffmpeg を別スレッドで実行して H.264 の MP4 に変換します。動画は `videos/` に保存されます。

### センサーと画像管理

`/jellylab` は温度・照度を取得して画面に渡します。`/status` はセンサー値、ストレージ容量、画像グループごとの枚数を JSON で返し、画面側がグラフと枚数表示を更新します。起動時に `start_logger()` が呼ばれる構成では、バックグラウンドスレッドが `LOG_INTERVAL` ごとにセンサー値を日次 CSV へ追記します。画像タイムラインではグループ移動、削除（`DEL_` 接頭辞への変更）、復元を行います。

## 設計上の制約・前提

1. **カメラデバイスは同時に二重オープンしない。** プレビュー、静止画、動画は一つの `CameraManager` とその `self.cap` を共有します。特に `record_video()` は「2つ目の VideoCapture は開かない」と明記され、既存カメラからフレームを読みます。デバイスやドライバーが複数のオープンを許さない可能性があるため、この共有を維持してください。
2. `CameraManager.open_capture()` は新しい `cv2.VideoCapture` を開く実装ですが、現在のコード上では呼び出されていません。呼び出しを追加すると二重オープンになり得ます。利用する場合は、共有カメラ設計との整合性を先に検討してください。
3. `reconnect()` は共有中のカメラを解放してから開き直します。別の独立したカメラを追加する処理ではありません。フレーム読み取りや撮影設定の操作は `self.lock` を通して共有カメラへの同時アクセスを抑えています。
4. Flask アプリはモジュール読み込み時にカメラを初期化します。したがって、現状の構成は一つのアプリプロセスが一つのカメラを所有する運用を前提とします。複数ワーカー／複数プロセスで起動すると、各プロセスが別々に同じデバイスを開こうとする可能性があります。運用例の systemd 設定は `python3 app.py` を単一サービスとして実行します。
5. カメラが接続されていること、設定されたデバイスパスが有効であること、動画変換を使う場合は `ffmpeg` が利用可能であることが必要です。温度・照度センサーは未接続または読み取り失敗時に `None` を返します。
6. データ保存先は `config.py` のプロジェクトルート基準です。`images/`、`micro_images/`、`videos/`、`logs/` は撮影・記録データを保存する場所です。

## 設計思想

- **カメラへのアクセスを一元化する:** ハードウェア資源を `CameraManager` に集約し、画面やルートが直接デバイスを開かないようにします。プレビューと録画の競合を避けるうえで、同じフレーム供給元を使うことが重要です。
- **Web 層と機器・処理層を分ける:** Flask のルートはリクエストを受けて処理を呼び出し、カメラ、センサー、ログ、画像集計はそれぞれのモジュールに委譲します。
- **長い処理は応答処理から分離する:** 動画録画とセンサー定期記録はスレッドで動かし、HTTP 応答や画面の表示を長時間ブロックしない構成です。
- **データの用途ごとに保存場所を分ける:** JellyLab の画像、Microscope の画像、動画、ログを別ディレクトリに分けます。ファイル名にはラベルや日時を含め、あとから一覧・分類しやすくしています。
- **機器がなくてもセンサー取得関数は失敗を値として返す:** センサー読み取り失敗は `None` として扱い、状態表示・記録側で欠測として処理します。一方、必須のカメラが起動時に開けない場合は、利用できない状態での起動継続を避けます。

## 変更時の確認事項

- カメラを使う新機能でも `CameraManager` の共有 `self.cap` を使い、別の `VideoCapture` を不用意に生成しないこと。
- 解像度変更を伴う撮影では、共有ロック内で切り替え・取得し、プレビュー設定へ戻すこと。
- 録画開始・停止ルート、画面の fetch、保存ディレクトリ、一覧・配信ルートの組み合わせを揃えること。
- Raspberry Pi 固有のカメラ、GPIO/I2C、`/sys`、systemd、ffmpeg に依存する機能は、対象機器での実行可否を確認すること。
